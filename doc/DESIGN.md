# Design

This is the one doc to read to understand the whole system. It covers what
each piece does, how a post moves through the system, and why the harder
decisions were made the way they were.

## What this is

A feed generation and ranking system, built from a public [Instagram-style
feed design doc](instagram_feed_design_doc.pdf). The goal was to build the
real thing, not a single-database demo with a paragraph about how it "would"
shard at scale: four independent Postgres shards, self-routing IDs, a real
graph database for the social graph, and a script that proves two
separately-written shard routers agree on every placement decision.

Each service is written in a different language, matching the role it would
realistically use in production: Go for the fast write path, Java for a
Kafka consumer, Python for embeddings, Node for a lightweight event
consumer, Rust for a stateless scorer.

## Goals

- Create posts, follow/unfollow, like/unlike, comment.
- Notify a user when they're `@mentioned`.
- Generate a ranked feed from three sources: people you follow, celebrities
  you follow, and similar content from people you don't follow.
- ~80,000 reads/second, p99 under 200ms (the source doc's target at 500M
  daily users).

## Not goals

- Not production-ready. No auth, no observability, no replicated stateful
  services, no resharding tooling. See [TRADE-OFFS.md](TRADE-OFFS.md) for
  the full list of what's simplified and why.
- Not a trained ranking model. Scoring is a transparent formula (recency ×
  engagement), not machine learning — training a real model needs logged
  production traffic this repo doesn't have.

## Architecture

```
                                   Client
                                     │
                        ┌─────────────────────────────┐
                        │        Envoy gateway           │
                        └──┬──────────────┬──────────────┬──┘
                /api/ingest│    /api/feed  │           /* │
                           ▼               ▼               ▼
   ┌────────────────────────────┐ ┌──────────────────────────────┐ ┌──────────────┐
   │ post-ingestion-service (Go) │ │ feed-aggregation-service (Go) │ │ web-ui        │
   └──┬─────────┬─────────┬──────┘ └──┬───────┬───────┬───────┬───┘ └──────────────┘
      ▼         ▼         ▼           ▼       ▼       ▼       ▼
  Postgres    Neo4j     Redis     Redis    Redis   BadgerDB  Qdrant
  4 shards   (graph)  (counters)   hot     celeb    cold     (search
                                   inbox   outbox   tier    by meaning)
                          │
                        Kafka "post-created"
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
 fanout-worker      vector-pipeline    notification-service
   (Java)              (Python)            (Node/TS)
```

One gateway (Envoy) is the only way in for real users. It sends writes to
`post-ingestion-service`, feed reads to `feed-aggregation-service`, and
everything else to the web UI.

| Service | Language | Job |
|---|---|---|
| post-ingestion-service | Go | Handles every write: new posts, follows, likes, comments. |
| fanout-worker | Java | Listens for new posts, decides whose inbox gets them. |
| vector-pipeline | Python | Turns a post's caption into a search vector. |
| notification-service | Node/TS | Sends a notification when someone is `@mentioned`. |
| feed-aggregation-service | Go | Builds a user's feed on demand: gathers candidates, ranks them, returns a page. |
| ranking-service | Rust | Scores a list of candidate posts. No database, no memory between calls. |

Two internal calls (fan-out's cold-tier write, and the ranking call) go
directly between services over gRPC, not through Envoy — they're internal
traffic on a private network, not client traffic crossing the internet, so
routing them through the edge gateway would just add a hop with no benefit.

## Data model

Postgres has the same schema on all 4 shards. Every ID is generated by the
app, never a database auto-increment — more on why below.

```sql
CREATE TABLE users (
    user_id BIGINT PRIMARY KEY,
    username VARCHAR(64) UNIQUE NOT NULL,
    last_active_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE TABLE posts (
    post_id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    media_url TEXT NOT NULL,
    media_type SMALLINT NOT NULL,
    caption TEXT,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);

CREATE TABLE likes (
    post_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    PRIMARY KEY (post_id, user_id)
);

CREATE TABLE comments (
    comment_id BIGINT PRIMARY KEY,
    post_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    body TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

Two things are missing on purpose:

- **No `follows` table.** A follow connects two users who can be on any two
  of the four shards. That's a graph relationship, not a relational one —
  it lives in Neo4j instead. See "Why Neo4j" below.
- **No `like_count`/`comment_count` column.** Counts live in Redis instead.
  See "Counters" below.

## The write path

What happens when a user posts:

1. Client sends `POST /v1/posts` to `post-ingestion-service`.
2. The post gets an ID that inherits the author's own shard — no
   re-hashing, so a post always lives where its author lives.
3. One `INSERT` into that shard's Postgres. This is the only step the
   client waits for.
4. The server publishes a `post-created` event to Kafka and immediately
   returns `201 Created`. Everything after this point happens in the
   background.
5. Three independent Kafka consumers each get their own copy of the event:
   - `fanout-worker` decides who should see the post next (below).
   - `vector-pipeline` embeds the caption for search.
   - `notification-service` checks for `@mentions` and notifies them.

### Fan-out: who gets the post, and how

This is the one decision worth slowing down for. Three different followers
get three different treatments:

- **A celebrity's followers:** the celebrity's post goes into one shared
  outbox. One write, no matter how many followers they have.
- **An active follower:** the post is pushed straight into their Redis
  inbox, because they're likely to open the app soon.
- **A dormant follower:** the post is written to a cheap disk-based store
  (BadgerDB) instead of Redis, and instead of being dropped.

Why three tiers, not one? Pushing to *everyone* wastes work on people who
rarely check the app. Never pushing to anyone (compute every feed fresh, on
every read) makes every read slow, including for people who check
constantly. The split picks the cheap option for each case: push where it's
likely to pay off, a cheap write where it might not, and skip push entirely
where even a cheap write doesn't scale (celebrities).

```java
if (socialGraph.isCelebrity(authorId)) {
    hotInbox.pushToCelebrityOutbox(authorId, postId, score);
    return;
}
List<Long> followers = socialGraph.getFollowers(authorId);
List<Long> activeFollowers = activity.filterActive(followers, activeWithinDays);
for (Long id : activeFollowers) hotInbox.pushToInbox(id, postId, score, feedInboxMaxItems);
for (Long id : dormantFollowers) coldTier.append(id, postId, score); // gRPC
```

A dormant follower's inbox lives on cheap disk until they come back — the
moment they open the app, it's promoted back into Redis, because a read
means they're active again now.

## The read path

What happens when a user opens their feed — `feed-aggregation-service`
runs these steps in order:

1. **Gather candidates from three sources, at the same time:** the user's
   Redis inbox (or the disk-based cold tier if the inbox is empty), the
   outboxes of celebrities they follow, and a similarity search (below).
2. **Merge and remove duplicates.**
3. **Drop anything the user has already been shown** in the last 48 hours.
4. **Fetch post details**, grouped by shard so it's a handful of batch
   queries, not one query per post.
5. **Score everything** with `ranking-service` (below).
6. **Apply business rules:** at most 2 posts per author, insert ads at
   fixed positions.
7. **Return a page and a cursor** for the next one.

### Scoring

`ranking-service` is a pure function: give it a list of candidates, get
back a score for each.

```rust
let score = weights.like * p_like
          + weights.comment * p_comment
          + weights.share * p_share
          - weights.hide * p_hide
          + weights.dwell * p_dwell;
```

It never touches a database and never sees which shard anything is on —
that's exactly why it's stateless and doesn't care what language calls it.

### Similarity search: the taste vector

The first two candidate sources only ever return posts from people you
already follow. On its own, that's a dead end for discovery — a new user
who follows three accounts gets three accounts' worth of posts, forever.

The fix: every post's caption is turned into a 384-number vector (an
embedding), where captions that mean similar things end up close together
in that space. To recommend for a user, the system averages the vectors of
their own and their followees' recent posts into one "taste vector," then
searches for posts near it.

Searching by comparing that vector against every post in the system would
be correct but far too slow at scale. Instead, the system uses **ANN**
(Approximate Nearest Neighbor) search — it finds matches that are almost
certainly among the closest, in a fraction of the time, by giving up a tiny
bit of precision. The specific technique, **HNSW**, works like a road
network: a few long "highway" links get you into roughly the right
neighborhood in a couple of hops, and shorter links at each level below
narrow it down step by step, without ever comparing against most of the
posts that were never going to be close matches anyway.

There's no fixed quota like "3 of every 20 posts must be from outside your
network" — similarity-search candidates compete for a spot using the same
score as everyone else. That's a deliberate choice (it means discovery
never crowds out a genuinely good in-network feed), and also a real
limitation (a user whose follows post constantly might see very little
outside their network on a given page).

### Pagination

Scrolling further doesn't use `OFFSET`/`LIMIT` against a list that keeps
changing — a new post arriving mid-scroll would shift everyone after it,
causing duplicates or skips. Instead, each response includes an encrypted,
opaque cursor. Scrolling is just the client sending that same cursor back;
the server decrypts it, re-runs the same pipeline, and picks up where the
last page left off.

## Why Neo4j, not a sharded `follows` table

A follow connects two users who can be on any of the four shards. The first
version of this repo sharded `follows` anyway, storing each edge twice —
once per user's shard. It worked, but every follow/unfollow became a
hand-rolled transaction across two separate databases, with no shared
transaction and a real chance the two copies could drift apart.

The social graph now lives in Neo4j instead:

```cypher
(:User {userId, username, followerCount, isCelebrity})
      -[:FOLLOWS {createdAt}]->
(:User)
```

Both directions ("who do I follow" and "who follows me") are fast, native
lookups. `followerCount` and `isCelebrity` update in the same transaction
that creates or removes the edge — nothing to keep in sync by hand.

## IDs that know their own shard

Every ID is a 64-bit number that carries its own shard number inside it:

```go
// 41 bits timestamp | 8 bits shard ID | 14 bits sequence
func ExtractShardID(id int64) int {
    return int(id>>shardIDShift) & MaxShardID
}
```

Finding where an *existing* row lives is a bit-shift, not a database
lookup. The only thing that still needs a decision is which shard a
brand-new signup lands on — that's the one job of a small consistent-hash
ring (150 virtual points per shard, so placement spreads evenly even with
only 4 real shards).

This exact scheme is implemented twice, independently, once in Go and once
in Java. A script feeds 10,000 sample IDs through both and checks they
agree on every single one — if they ever silently disagreed, one service
could create a user on shard 2 while another writes related data to shard
3, corrupting the data with no error at the time it happens.

## Counters live in Redis, not Postgres

A like is written on the *liker's* shard, but the count needs to be read
wherever the post shows up — which is the *author's* shard. Those are
often different shards, so keeping an accurate count in Postgres would mean
a cross-shard write on every single like.

Instead, counts live entirely in Redis, split across 16 sub-keys per post
so one viral post doesn't turn into one very hot Redis key. The `likes`
table still records who liked what (that's the real data); only the
fast-moving aggregate number moved out of Postgres.

## Internal wire formats

Two internal calls (the cold-tier write, and the ranking call) use gRPC
with a typed schema instead of hand-rolled JSON, so a field-name typo is a
compile-time error in every language instead of a silent runtime bug.

The Kafka event and the ranking call's payload use FlatBuffers instead of
Protobuf's own encoding. The reason is fan-out: one Kafka event gets read
independently by three different consumers, and Protobuf has to fully
parse a message before any field is usable — paid once per consumer, per
message. FlatBuffers reads a field straight out of the raw bytes, no parse
step. On the ranking call specifically, that matters because a single feed
request can carry hundreds of candidates in one call, on the most
latency-sensitive path in the system.

## What's simplified

Four shards instead of hundreds. One Neo4j instance and one Kafka broker
instead of replicated clusters. A scoring formula instead of a trained
model. Every one of these is a named trade-off, not an oversight — see
[TRADE-OFFS.md](TRADE-OFFS.md) for the full list and what to build first
toward production.
